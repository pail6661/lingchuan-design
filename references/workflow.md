# Workflow：从接到任务到交付

这份文件是三方向选定之后的主干流程，以及首轮需求问题的题库。视觉参考的前置判断、主动发现、确认/委托和失败降级统一见 `references/design-context.md`，这里不另建一套问答。

## 标准流程（三方向选定之后）

1. **复用已确认需求**：读本项目 spec、`visual-reference.md`、`direction-approved.md` 和已有事实记录，已回答的不再问。涉及会变化的具体产品/技术/事件时核实当前事实，记录来源；小修小补只核本次影响部分。三方向豁免不等于参考、事实与素材都可忽略。
2. **复用资源、补核心缺项**：已读过的 design system、链接、截图、代码与品牌资产直接复用。涉及品牌仍需 `brand-spec.md`；缺产品图/Logo/UI 等必要资产时只补缺项，避免再次向用户抛整张清单。视觉参考仅用于表达语言，不能代替真实品牌资产。
3. **先答 form 五问，再规划系统**（每个页面、屏幕、镜头开工前）：
   - **叙事角色**：hero / 过渡 / 数据 / 引语 / 结尾？
   - **观众距离**：10cm 手机 / 1m 笔记本 / 10m 投屏？决定字号和密度
   - **视觉温度**：安静 / 兴奋 / 冷静 / 权威 / 温柔 / 悲伤？
   - **容量估算**：画 3 个 5 秒小草图，算内容塞不塞得下
   - **视觉母题**：这个内容独有、别的题材不会有的视觉元素、结构或隐喻是什么？答不出说明还在靠风格标签抽签

   答完将设计系统（色彩、字型、版式节奏、组件模式）落实到选定方向，交付时写一句「form 来自内容的哪里」。这是助手的设计推导，不是新的一轮用户问卷；参考、系统和方向都已确认时直接执行。若要推翻已选参考或改主要结构，再说明变化并取得相应选择。
4. **建文件夹**：`项目名/` 下放主 HTML 和需要的素材（不要整批复制 >20 个文件）。
5. **对齐 pass**：HTML 开头写必要的 assumptions、占位和设计依据。选定的三方向初稿已经覆盖主要布局时，直接细化；新增重要页面或未确认的结构可先做局部灰稿，只有需要新取舍时再等待用户，不为同一决定重复停等。
6. **Full pass**：填占位、做变体、加 Tweaks。中间展示进度与变化，常规细化不再要求一次“批准继续”。
7. **验证**：Playwright 截图、查控制台报错、`python3 "$HD/scripts/design_lint.py" check`（红灯必修）。🛑 交付前自己肉眼过一遍浏览器——AI 写的交互经常有 bug。
8. **交付与回流**：总结只说 caveats 和下一步；`design_lint.py ledger add` 记外观账；`learn.py harvest` 看有什么值得记（`references/evolution.md`）。

**检查点原则**：待选参考、待选真实方案或会改变已确认范围的重大取舍，需要清楚展示后等选择；已有明确指令或委托就按其范围继续。参考与方案分别记录，用户沉默不算批准。文字总结、设计系统复述、常规细化不是额外的强制确认轮。

## 异常处理

| 场景 | 处理 |
|---|---|
| 需求模糊到无法着手 | 列 3 个可能的方向（如「落地页 / Dashboard / 产品详情页」）让用户选，不要直接问 10 个问题 |
| 用户说「不要问了，直接做」 | 不重复需求问卷；能从当前材料确定的参考直接沿用，缺参考先做可看展示，不将泛泛“直接做”冒充选图。若明确“参考你定”，记录委托后推进；只有明确跳过三方向时才按其范围减免，并在 `direction-approved.md` 留原话 |
| 参考图和品牌规范打架 | 停下，指出具体矛盾（「截图是衬线，规范写的是无衬线」），让用户选 |
| 起手组件加载失败 | 先查 `references/react-setup.md` 的报错表；还不行就降级纯 HTML+CSS |
| 时间紧，「30 分钟内要」 | 优先复用已有参考，缩小页面/片段与候选细节；时限本身不等于授权选参考或免三方向。用户明确委托或减免后按记录执行，不暗中省去选择 |
| 单个 HTML >1000 行 | 按 `references/react-setup.md` 拆成多个 jsx，末尾 `Object.assign(window, …)` 共享 |
| 克制原则和产品需要的信息密度冲突 | 产品卖点是 AI、数据、上下文感知（Dashboard、Tracker、Copilot、健康、记账）时走高密度：每屏 ≥3 处有内容的差异化信息；装饰性 icon 照样不要 |

异常时先用一句话告诉用户发生了什么，再按表处理，不要静默决策。

## 问问题的艺术

首轮把真正缺失、会影响结果的问题合并，通常最多 3 个；下面是题库，不是必填问卷。先读现有信息，能确定的就不问。用户明确没有参考时由助手去找，不再要求用户先给出专业风格词。后续只补新出现的关键冲突，不重复首轮；未获回复时可以继续资料整理与参考发现，不能把待选的参考或方案写成已选。

**什么时候需要问**：目标/媒介无法确定，已观察的参考存在重要冲突，或到了用户需要选择的步骤且没有明确委托。新任务本身不意味着必须问固定问题。

**什么时候可以不问**：小修小补、follow-up任务、用户已经给了明确PRD+截图+上下文。

**怎么问**：大部分 agent 环境没有结构化问题 UI，在对话里用 markdown 清单问即可。**一次性把问题列完让用户批量答**，不要一来一回一个个问——那会浪费用户时间、打断用户思路。

## 需求题库（只补缺项）

按当前任务选择必要类别；已给材料足够时可以没有前置问题。

### 1. Design Context（最重要）

- 先核对已有 design system、品牌指南、截图、链接和代码，不重问。
- 未知是否有视觉参考时，按 `references/design-context.md` 温和问一次；明确没有则主动提供可看选择。

同一项目的已确认参考继续有效，除非用户要求换方向或新媒介需要补充。参考确认后再进入新方案探索，不以“只能凭直觉”给用户施压。

### 2. Variations维度

- 三方向之外，用户还想在哪些维度上看变体？（三个方向本身是固定的，不用问要几种）

### 3. Fidelity和Scope

- 多高保真？线框图 / 半成品 / 真实data的full hi-fi？
- 覆盖多少flow？一屏 / 一个flow / 整个产品？
- 有没有具体的「必须包含」元素？

### 4. Tweaks

- 希望能实时调整哪些参数？（颜色/字号/间距/layout/文案/feature flag）
- 用户自己要不要在做完后继续调？

### 5. 任务专属缺项

只问会改变交付的细节，不设问题数量下限。例如：

**做landing page**：
- 目标转化动作是什么？
- 主要受众？
- 竞品参考？
- 文案谁提供？

**做iOS App onboarding**：
- 几步？
- 需要用户做什么？
- 跳过路径？
- 目标留存率？

**做动画**：
- 时长？
- 最终用途（视频素材/官网/社交）？
- 节奏（快/慢/分段）？
- 必须出现的关键帧？

## 问题模板示例

按缺项改写，不能原样追加已知信息；例如只剩参考和阅读场景未知时：

```markdown
资料里的文案、尺寸和品牌文件已经够用了，我先按这些来。
1. 这份主要在手机上读，还是用于现场投屏？
2. 有想参考的图片或页面吗？没有的话我来找几组给你挑。
```

## 早对齐模式

这是整个workflow最重要的环节。**不要接到任务就闷头冲**。步骤：

### Pass 1：Assumptions + Placeholders（5-15分钟）

HTML文件头部先写你的**assumptions+reasoning comments**，像junior给manager汇报：

```html
<!--
我的假设：
- 这是给XX受众看的
- 整体tone我理解为XX（基于用户说的"专业但不严肃"）
- 主要flow是A→B→C
- 色彩我想用品牌蓝+暖灰，不确定你想不想要accent色

未解的问题：
- 第3步的数据从哪里来？先用placeholder
- 背景图用抽象几何还是真照片？先占位

如果你看到这里觉得方向不对，现在是成本最低的时候改。
-->

<!-- 然后是带placeholder的结构 -->
<section class="hero">
  <h1>[主标题位 - 等用户提供]</h1>
  <p>[副标题位]</p>
  <div class="cta-placeholder">[CTA按钮]</div>
</section>
```

保存后展示。已有方向与布局批准时，继续细化；这个灰稿提出新的重要结构取舍时才等用户选择，不重复审批已确定内容。

### Pass 2：真实组件+Variations（主力工作量）

用户批准方向后，开始填充。这时：
- 写React组件替换placeholder
- 做variations（用design_canvas或Tweaks）
- 如果是幻灯片/动画，用starter components起手

中间给一次可看的进度，指出相对已选方向的变化；除非需要新决策，不把进度汇报变成强制停等。

### Pass 3：细节打磨

用户满意整体后，打磨：
- 字号/间距/对比度微调
- 动画timing
- 边界case
- Tweaks面板完善

### Pass 4：验证+交付

- 用Playwright截图（见`references/verification.md`）
- 打开浏览器肉眼确认
- 总结**极简**：只说caveats和next steps

## Variations的深度逻辑

给variations不是给用户制造选择困难，是**探索可能性空间**。让用户mix and match出最终版本。

### 好的variations长什么样

- **维度明确**：每个variation在不同维度上变（A vs B只换配色，C vs D只换layout）
- **有梯度**：从「by-the-book保守版」到「大胆novel版」逐级递进
- **有记号**：每个variation有短label说明它在探索什么

### 实现方式

**纯视觉对比**（静态）：
→ 用`assets/design_canvas.jsx`，网格布局并排展示。每个cell带label。

**多选项/交互差异**：
→ 做完整原型，用Tweaks切换。例如做登录页，"布局"是tweak的一个选项：
- 左文案右表单
- 顶部logo+中央表单
- 背景全屏图+浮层表单

用户开关Tweaks就能切换，不需要打开多个HTML文件。

### 探索矩阵思考

每次设计，脑内过一遍这些维度，挑2-3个来给variations：

- 视觉：minimal / editorial / brutalist / organic / futuristic / retro
- 色彩：monochrome / dual-tone / vibrant / pastel / high-contrast
- 字型：sans-only / sans+serif对比 / 全衬线 / 等宽
- Layout：对称 / 非对称 / 不规则grid / full-bleed / 窄栏
- Density：稀疏呼吸 / 中等 / 信息密集
- 交互：极简hover / 丰富micro-interaction / 夸张大动画
- 材质：flat / 有阴影层次 / 纹理 / noise / 渐变

## 遇到不确定的情况

- **不知道怎么做**：坦白说你不确定，问用户，或先做个placeholder继续。**不要编**。
- **用户的描述矛盾**：指出矛盾，让用户选一个方向。
- **任务太大一次吃不下**：拆成steps，先做第一步让用户看，再推进。
- **用户要求的效果技术上很难**：说清技术边界，提供替代方案。

## 总结规则

交付时，summary **极短**：

```markdown
✅ 幻灯片已完成（10张），带Tweaks可切换"夜/日模式"。

注意：
- 第4页的数据是假的，等你提供真数据我替换
- 动画用了CSS transition，不需要JS

下一步建议：先你浏览器打开看一遍，有问题告诉我哪页哪处。
```

不要：
- 罗列每一页的内容
- 重复讲你用了什么技术
- 夸自己设计多好

Caveats + next steps，结束。
