# Design Context：从已有上下文出发

这是凌川 1.0.1 的视觉参考对齐流程。先看用户已经给了什么，再决定是否需要问；缺参考时由助手主动找可看的方向，帮助用户选择，而不是把找参考的工作推回去。

适用于网页、App、PPT、信息图和动画等新视觉设计。局部改字、修错、导出，以及同项目已选方向的迭代沿用现有记录；更换视觉方向时只重新对齐受影响部分。

## 什么是Design Context

先区分三类输入：文案/数据说明“讲什么”；视觉参考说明“希望怎样表达”；品牌规范与现有系统约束“必须保留什么”。用户给了内容资料不代表已经选了视觉方向。当前明确指令优先于历史偏好；与品牌硬约束冲突时指出具体矛盾，不静默覆盖。

可用的视觉上下文包括：

### 1. 用户的Design System/UI Kit
用户自己产品已有的组件库、色彩token、字型规范、icon系统。**最完美的情况**。

### 2. 用户的Codebase
如果用户给了代码库，里面就有活生生的组件实现。Read那些组件文件：
- `theme.ts` / `colors.ts` / `tokens.css` / `_variables.scss`
- 具体的组件（Button.tsx、Card.tsx）
- Layout scaffold（App.tsx、MainLayout.tsx）
- Global stylesheets

**读代码抄exact values**：hex codes、spacing scale、font stack、border radius。不要凭记忆重画。

### 3. 用户已发布的产品
如果用户有上线的产品但没给代码，用Playwright或让用户提供截图。

```bash
# 用Playwright截图一个公开URL
npx playwright screenshot https://example.com screenshot.png --viewport-size=1920,1080
```

让你看到真实的视觉vocabulary。

### 4. 品牌指南/Logo/已有素材
用户可能有：Logo文件、品牌色规范、营销物料、slide模板。这些都是context。

### 5. 竞品参考
用户说“像 XX 网站那样”——优先打开已给链接；仅给名字时主动查找可核实的页面或截图，找不到再索取。**不要**凭训练数据里的模糊印象描述其外观。

### 6. 已知的design system（fallback）
参考发现的一种来源是已知设计系统，例如：
- Apple HIG
- Material Design 3
- Radix Colors（配色）
- shadcn/ui（组件）
- Tailwind默认palette

展示真实可见的样例并说明为何适用；这些名称不是用户已确认的视觉方向，也不要求自动安装组件库。

## 一次任务怎样对齐

### 1 · 先读材料，判断参考状态

检查本轮附件、链接、当前项目已确认记录和可访问的现有产品。优先读取相关文件，不要求用户重新发已经能打开的资料。读取代码库时找主题/token、全局样式和代表性组件，提取本任务需要的实际值；不为凑固定数量读无关文件。

| 状态 | 下一步 |
|---|---|
| 用户已明确指定参考及用途 | 实际查看后提炼并复述，直接记录已确认，沿用授权推进 |
| 给了图/链接，但用途或借鉴点含糊 | 先看再问一个关键点，例如“主要想借它的排版，还是配色？” |
| 多个参考且取舍已明确 | 按“借 A 的结构、B 的配色，避开 C 的密度”记录；可兼容就不重问 |
| 多个参考有实质冲突 | 说明冲突对本任务的影响，推荐一种组合，仅让用户定需要取舍的部分 |
| 只给文案/数据、没说有没有视觉参考 | 在本轮缺项里温和问一次；不把资料齐全误写成风格已确认 |
| 用户已说明没有参考 | 直接进入主动找参考，不再追问“你喜欢哪种风格” |
| 本项目已有确认且任务未变 | 复用其适用范围；新增视觉媒介或重构需求时只补有变化的部分 |

推荐的首轮说法：

> 我先看你给的资料。你有想参考的图片、页面、PPT 或视频片段吗？有的话我会先拆一下想借鉴的部分；没有也没关系，我可以先找几组不同的视觉参考给你挑。

已有资料时换成具体反馈，例如：

> 这两张我看到了。我会借 A 的大标题与留白、B 的图文比例，保留你的品牌色；截图里的装饰不照搬。接下来就在这个范围里探索方案。

示例只能在实际看过后使用。读不到的文件或链接先说明，不写“我看到了”。已确定的媒介/尺寸/受众不重问，其余真正影响结果的缺项合并提问，通常不超过 3 个。

### 2 · 没有参考，由助手主动找

先按媒介、受众、信息密度、用途与品牌约束检索。PPT 优先看封面加内容/数据页；App 看相关任务的屏幕和流程；网页看真实页面及手机状态；信息图看实际阅读尺寸；动画看关键帧和一小段运动，不能只凭海报判断节奏。

优先用作者/机构原始页面、用户指定来源和可访问的公开作品。通常选 2–3 组有实质差异的参考，够判断就停止扩搜；不为凑数进行固定轮数的无效检索。允许有理由的跨媒介启发，但说明哪些语言能迁移、哪些不能迁移。

用当前宿主实际可用的浏览器、图片查看、文档预览或截图能力观察。`scripts/ref_board.py` 只是可选工具，缺它不等于不能看参考；不为展示参考自动安装依赖。只能读到搜索摘要/文字/链接时，记录“未观察到画面”，不做想象分析。

每组展示一张或数张可见画面（动画可加片段/关键帧），附简短卡片：

| 要点 | 记录内容 |
|---|---|
| 来源与观察 | 作者/项目、原链接或本地样张路径、实际打开的页/片段；仅看静帧就只写静帧 |
| 适合本任务的原因 | 和受众、内容及媒介的关系 |
| 借鉴点 | 网格、标题与正文关系、图文比例、密度、材质或运动节奏等具体规则 |
| 不照搬的部分 | 第三方 Logo/文案、无关装饰、与品牌或可读性冲突的细节 |
| 推荐与取舍 | 推荐哪组或怎样组合，说明理由 |

推荐反馈：

> 我找了三组参考：A 更适合清楚讲数据，B 更有杂志感，C 更有亲和力。结合你的受众，我倾向 A 的结构配 B 的标题。你更接近哪一组，也可以告诉我想保留哪些部分；确定后我再用你的内容做三个方案。

“A/B/C”须对应实际展示的画面，不能用三个形容词代替。参考用于理解视觉语言，不自动成为可复制或可商用的素材；需要进入成品的照片、Logo 等另走素材与品牌协议。

### 3 · 检索或展示能力不足时

- 链接打不开：换同一作品的公开图片/作者页面；必要时请用户补截图，不反复索取已能读取的材料。
- 外部检索不可用：查看并展示技能已有的风格样张，明确标“本地样张”，不是新找到的真实项目。按当前媒介选库，不默认让所有设计都从通用 Web UI 起步。
- 需要自己探索画面：能力确实可用且当前任务授权、费用条件允许时，可制作小型 HTML 草图或生成探针图，标“自制探针/AI 生成方向”，不是外部参考，也不是完成稿。不要为普通 PPT/App 任务默认强制生图。
- 连样张或探针也无法查看/展示：坦诚说明缺什么，给最小替代办法。可以继续整理内容、核实事实和资产；未经选择或明确委托，不跳到某个新视觉方向，也不把不存在的图写成已展示。

没有参考不等于用户需求差，也不能据此断言最终质量低；下一步是帮助其建立可讨论的视觉依据。

### 4 · 记录一次，再进入方案探索

在项目的 `visual-reference.md` 中简记以下信息即可，不复制所有参考图片进技能仓库：

```markdown
# 本项目视觉参考
状态：pending / confirmed / delegated（实际保留一个）
适用范围：媒介、页面/段落、当前需求版本
来源与观察：原链接/文件；看了哪页/片段；哪些尚未看见
借鉴：具体规则
避开与硬约束：不借什么，品牌/内容必须保留什么
依据：用户原话及当前上下文，或明确委托选参考的原话
未决项：有就写；无就写无
```

- `confirmed`：用户已经指定了可理解的参考范围，或对刚展示的参考作了明确选择；不要求再说一次“确认”。
- `delegated`：用户明确让助手选参考。记录推荐与理由后可推进；仅说“帮我找一下”只授权检索，不等于授权选定。
- `pending`：尚未选择或存在影响方向的冲突。没有回复、时间经过、生成文件都不能把它变为已确认。

“继续”可确认刚展示且指向明确的推荐；泛泛“直接做”不能冒充选中了某张图。可先做便于选择的参考展示，后续三方向规则仍适用。若用户明确“参考和方案都由你定，不用等我”，分别记录委托与三方向豁免的依据，不扩大到其他外部动作。

参考确认是在选表达语言，`direction-approved.md` 是在选本任务生成的方案，二者不互相冒充。进入 `references/directions.md` 后，已确认的参考/品牌约束作为共同输入；现实参照尽量复用已有观察，轮盘也在可兼容范围内探索。外观账本只提醒自由探索时避免惯性重复，不能否决用户已选参考、品牌连续性或同项目延续。用户选定真实方案后，不再为同一参考、同一系统和同一方向追加确认；只有重大改变才重新对齐。

临时参考选择留在本项目。用户没有说明是长期偏好时，不自动改全局品味记录。

## Import策略（用户给了codebase）

如果用户说"import这个codebase做参考"：

### 小型（<50文件）
全部Read，把context内化。

### 中型（50-500文件）
Focus在：
- `src/components/` 或 `components/`
- 所有styles/tokens/theme相关的文件
- 2-3个代表性的整页组件（Home.tsx、Dashboard.tsx）

### 大型（>500文件）
优先从当前任务判断 focus，仍不明确再问一个定位问题：
- "我要做settings页面" → 读现有的settings相关
- "我要做一个新的feature" → 读整体shell + 最接近的参考
- 不求全，求准

## 和Figma/设计稿的配合

如果用户给了Figma链接：

- 先用当前可用的连接或工具打开；能取得画面与属性就直接读取，不要求重复导出。
- 链接无权限或缺相应能力时，请用户提供截图或导出；不声称已读取设计节点。

如果只给了Figma截图，告诉用户：
- 我能看到视觉，但取不到精确values
- 本任务确需精确复现时再补关键数值；仅作视觉灵感时，不必先索要整套 token。

## 最后的提醒

先帮助用户建立看得见、能讨论的视觉依据，再把这个依据转换成自己的设计。复用已确认的信息，只问真正影响下一步的缺项。
